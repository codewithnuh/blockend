The rate limiter counts requests per key in a fixed time window. When a key passes the limit, the adapter returns 429 and stops the request before it reaches your route.

The block has no root `index.ts`. Import adapters from `adapters/`, stores from `variants/`, and shared types from `core/core`.

## Quick start

```bash
pnpm dlx blockend-cli init
pnpm dlx blockend-cli add rate-limiter
```

```ts
import express from "express";
import { expressRateLimit } from "@/blocks/rate-limiter/adapters/express";
import { MemoryStore } from "@/blocks/rate-limiter/variants/memory-store";

const app = express();
const store = new MemoryStore();

app.use(
  expressRateLimit({
    windowMs: 60_000,
    max: 100,
    store
  })
);

app.get("/", (_req, res) => {
  res.json({ ok: true });
});
```

## Configuration

Every adapter accepts the same options:

```ts
{
  store: RateLimitStore;
  windowMs?: number;
  max?: number;
  statusCode?: number;
  message?: string | Record<string, unknown>;
  standardHeaders?: boolean;
  legacyHeaders?: boolean;
  keyGenerator?: (request) => string;
}
```

| Option            | Default                                                   | Description                                                                 |
| ----------------- | --------------------------------------------------------- | --------------------------------------------------------------------------- |
| `store`           | Required                                                  | `MemoryStore` or `RedisStore`.                                              |
| `windowMs`        | `60000`                                                   | Window length in milliseconds.                                              |
| `max`             | `100`                                                     | Requests allowed per key per window.                                        |
| `statusCode`      | `429`                                                     | Status returned when the limit is exceeded.                                 |
| `message`         | `{ error: "Too many requests, please try again later." }` | Response body.                                                              |
| `standardHeaders` | `true`                                                    | Adds `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset`.       |
| `legacyHeaders`   | `true`                                                    | Adds `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset`. |
| `keyGenerator`    | Client IP                                                 | Returns the key to count.                                                   |

`max` is the number of allowed requests. Request `max + 1` is blocked.

## Usage

### Express

```ts
import express from "express";
import { expressRateLimit } from "@/blocks/rate-limiter/adapters/express";
import { MemoryStore } from "@/blocks/rate-limiter/variants/memory-store";

const app = express();
const store = new MemoryStore();

app.use(
  expressRateLimit({
    windowMs: 60_000,
    max: 100,
    store
  })
);
```

For a limit per authenticated user, mount the limiter after your auth middleware and use the user ID. The example assumes your auth middleware declares `req.user` on Express's request type:

```ts
app.use(
  "/api",
  expressRateLimit({
    windowMs: 60_000,
    max: 300,
    store,
    keyGenerator: (req) => req.user.id
  })
);
```

### Fastify

```ts
import Fastify from "fastify";
import { fastifyRateLimit } from "@/blocks/rate-limiter/adapters/fastify";
import { MemoryStore } from "@/blocks/rate-limiter/variants/memory-store";

const app = Fastify();
const store = new MemoryStore();

app.addHook(
  "onRequest",
  fastifyRateLimit({
    windowMs: 60_000,
    max: 100,
    store
  })
);

await app.listen({ port: 3000 });
```

### Hono

```ts
import { Hono } from "hono";
import { honoRateLimit } from "@/blocks/rate-limiter/adapters/hono";
import { MemoryStore } from "@/blocks/rate-limiter/variants/memory-store";

const app = new Hono();
const store = new MemoryStore();

app.use(
  "*",
  honoRateLimit({
    windowMs: 60_000,
    max: 100,
    store
  })
);

export default app;
```

## Stores

### MemoryStore

`MemoryStore` keeps counters in a `Map` in the current process. It cleans expired keys on a one-minute interval. Use it for a single process, local development, or tests.

It does not share state between app instances. Each instance gets its own limit, so a two-instance deployment effectively doubles the allowed request count.

### RedisStore

`RedisStore` uses an `ioredis` client and a Lua script. The increment and expiry setup run atomically, so multiple instances share one counter.

```ts
import { Redis } from "ioredis";
import { RedisStore } from "@/blocks/rate-limiter/variants/redis-store";

const redis = new Redis(process.env.REDIS_URL!);

const store = new RedisStore(redis, "rl:");
```

The constructor signature is:

```ts
new RedisStore(redisClient, (keyPrefix = "rl:"));
```

`keyPrefix` separates rate limit keys from other data in the same Redis database. Use a different prefix per environment or application.

If Redis is unavailable, the adapter logs the error and lets the request continue. The route is unprotected during the outage. Decide whether that is acceptable for the endpoint.

## Key generation

The default key is the client IP from `x-forwarded-for`, then `x-real-ip`, then the socket address. The Hono adapter has no socket address in `Context`, so it falls back to `"unknown-ip"` when both headers are missing. Behind a proxy that overwrites those headers, that is fine. Without one, every Hono client shares a single key.

<Callout type="warn">
  `getClientIp` trusts `x-forwarded-for` and `x-real-ip` without checking whether the request came
  from a trusted proxy. If your app is reachable directly, a client can send its own header and
  choose a new key for every request. Run the app behind a proxy that overwrites these headers, or
  pass a `keyGenerator` that uses a value you control.
</Callout>

For authenticated routes, use the user or tenant ID. This example assumes your auth middleware sets `req.user`:

```ts
keyGenerator: (req) => `user:${req.user.id}`; // Express or Fastify
```

On Hono, read the user from context:

```ts
keyGenerator: (c) => `user:${c.get("user").id}`;
```

For unauthenticated routes, a normalized IP is reasonable:

```ts
keyGenerator: (req) => req.ip ?? req.socket.remoteAddress ?? "unknown"; // Express or Fastify
```

## Behavior

The limiter uses a fixed window, not a sliding window or token bucket. A key gets `max` requests per window. Traffic can burst at a window boundary: 100 requests at the end of one window and 100 at the start of the next are both allowed.

When the store call succeeds, headers are set on both allowed and blocked responses:

| Header                | Meaning                                                       |
| --------------------- | ------------------------------------------------------------- |
| `RateLimit-Limit`     | Maximum requests and window length, such as `100, window=60`. |
| `RateLimit-Remaining` | Requests left after this one.                                 |
| `RateLimit-Reset`     | Seconds until the window resets.                              |
| `Retry-After`         | Seconds until the client can retry. Only set when blocked.    |
| `X-RateLimit-Reset`   | Absolute Unix timestamp in seconds.                           |

When the store throws, the adapter fails open. Express and Hono call `next()`, Fastify continues the request. Check your logs for `Rate limiter failure`.

## API reference

### `expressRateLimit`

```ts
function expressRateLimit(options: ExpressOptions): RequestHandler;
```

`ExpressOptions` extends `Partial<RateLimitConfig>` with `store` and `keyGenerator`.

### `fastifyRateLimit`

```ts
function fastifyRateLimit(options: FastifyOptions): preHandlerHookHandler;
```

Register it as an `onRequest` hook or a route pre-handler.

### `honoRateLimit`

```ts
function honoRateLimit(options: HonoOptions): MiddlewareHandler;
```

Register it with `app.use`.

### `evaluateRateLimit`

```ts
function evaluateRateLimit(
  key: string,
  store: RateLimitStore,
  config: RateLimitConfig
): Promise<RateLimitResult>;
```

Runs one increment and returns `isBlocked`, `statusCode`, `message`, and headers. Use it if you need a custom adapter.

### `RateLimitStore`

```ts
interface RateLimitStore {
  increment(key: string, windowMs: number): Promise<RateLimitRecord> | RateLimitRecord;
}

interface RateLimitRecord {
  hits: number;
  resetTime: number; // Unix timestamp in milliseconds
}
```

A custom store must increment atomically. A read-then-write implementation can let concurrent requests pass the limit.

## Production notes

- Use Redis when you run more than one process or container.
- Put the limiter before expensive routes and before auth work you want to protect.
- For per-user limits, put the limiter after auth so the user ID is available.
- Set `windowMs` and `max` from your traffic profile. A global 100 requests per minute will block API clients that legitimately batch requests.
- Alert on Redis errors. Fail-open behavior is intentional, but it means the limit is not enforced during an outage.
- Add a separate limit for login, password reset, and other credential endpoints. A global limit is not a brute-force defense.

## When not to use it

- You need distributed coordination across regions with strict limits. A single Redis instance is still a single point of failure.
- You need per-endpoint cost weighting. This block counts requests, not units of work.
- You need a sliding window with no boundary burst. Use a different algorithm.
