The **Rate Limiter** block protects your application from abuse by limiting how many requests a client can make within a configurable time window.

It is built around a framework-independent core engine with lightweight framework adapters and pluggable storage backends for Memory and Redis.

---

## Features

- Framework-agnostic core engine
- Express, Fastify, and Hono adapters
- Memory and Redis stores
- Configurable time window and request limit
- Custom key generation
- RFC-compliant `RateLimit-*` headers
- Legacy `X-RateLimit-*` headers
- `Retry-After` header on blocked requests
- Fail-open behavior on store errors
- Fully typed

## File Structure

```text
rate-limiter
├── adapters
│   ├── express.ts
│   ├── fastify.ts
│   └── hono.ts
├── core
│   └── core.ts
├── utils
│   └── ip.ts
└── variants
    ├── memory-store.ts
    └── redis-store.ts
```

- **adapters/** — Framework-specific middleware that extracts client identifiers, invokes the core engine, and applies response headers.
- **core/** — The `evaluateRateLimit` engine and shared TypeScript interfaces (`RateLimitConfig`, `RateLimitStore`, `RateLimitRecord`, `RateLimitResult`).
- **utils/** — `getClientIp` utility for extracting the client IP from request headers.
- **variants/** — Storage implementations: `MemoryStore` (in-memory map with periodic purging) and `RedisStore` (atomic Lua script via ioredis).

## Configuration

| Option            | Type                                | Default                                                   | Description                            |
| ----------------- | ----------------------------------- | --------------------------------------------------------- | -------------------------------------- |
| `windowMs`        | `number`                            | `60000`                                                   | Time window in milliseconds            |
| `max`             | `number`                            | `100`                                                     | Maximum requests allowed within window |
| `store`           | `RateLimitStore`                    | Required                                                  | Storage implementation                 |
| `keyGenerator`    | `(req) => string`                   | Client IP (`getClientIp`)                                 | Unique identifier for each client      |
| `statusCode`      | `number`                            | `429`                                                     | HTTP status code when rate limited     |
| `message`         | `string \| Record<string, unknown>` | `{ error: "Too many requests, please try again later." }` | Response body when rate limited        |
| `standardHeaders` | `boolean`                           | `true`                                                    | Emit `RateLimit-*` headers             |
| `legacyHeaders`   | `boolean`                           | `true`                                                    | Emit `X-RateLimit-*` headers           |

## Architecture

```text
Request
   │
   ▼
Express / Fastify / Hono Adapter
   │  (extracts client key, calls evaluateRateLimit)
   ▼
evaluateRateLimit (core engine)
   │  (increments counter via store)
   ▼
MemoryStore / RedisStore
   │  (returns hits + resetTime)
   ▼
Core engine computes headers
   │
   ▼
Adapter applies headers + returns 429 or passes through
```

The adapter extracts a client identifier, calls `evaluateRateLimit` with the key, store, and configuration, then applies the returned headers to the response. If the client exceeds the limit, the adapter returns a `429 Too Many Requests` response. If the store throws, the error is logged and the request continues (fail-open).

## When to Use

- You need rate limiting across multiple frameworks (Express, Fastify, Hono) from a shared core.
- You want to switch between in-memory and Redis storage without changing application code.
- You prefer generated source code you own over opaque npm dependencies.

## When Not to Use

- You only need Express rate limiting and prefer a zero-config solution like `express-rate-limit`.
- You do not need pluggable storage or framework-agnostic architecture.

## Usage

### Express

```ts
import { expressRateLimit } from "@/blocks/rate-limiter/adapters/express";
import { MemoryStore } from "@/blocks/rate-limiter/variants/memory-store";

app.use(
  "/api",
  expressRateLimit({
    windowMs: 60_000,
    max: 100,
    store: new MemoryStore()
  })
);
```

## API Reference

#### evaluateRateLimit

Core engine that checks and increments the rate limit for a given key.

```ts
async function evaluateRateLimit(
  key: string,
  store: RateLimitStore,
  config: RateLimitConfig
): Promise<RateLimitResult>;
```

**Parameters**

| Name     | Type              | Required | Description                         |
| -------- | ----------------- | -------- | ----------------------------------- |
| `key`    | `string`          | Yes      | Unique client identifier            |
| `store`  | `RateLimitStore`  | Yes      | Storage backend to persist counters |
| `config` | `RateLimitConfig` | Yes      | Rate limit configuration            |

**Returns**

`RateLimitResult` with `isBlocked`, `statusCode`, `message`, and `headers`.

#### expressRateLimit

Creates Express middleware for rate limiting.

```ts
function expressRateLimit(options: ExpressOptions): (req, res, next) => Promise<void>;
```

#### fastifyRateLimit

Creates a Fastify `onRequest` hook for rate limiting.

```ts
function fastifyRateLimit(options: FastifyOptions): (request, reply) => Promise<void>;
```

#### honoRateLimit

Creates Hono middleware for rate limiting.

```ts
function honoRateLimit(options: HonoOptions): MiddlewareHandler;
```

#### MemoryStore

In-memory store using a `Map` with a chronological expiration queue and periodic purge.

```ts
class MemoryStore implements RateLimitStore
```

#### RedisStore

Redis store using an atomic Lua script to increment and set expiry in one round-trip.

```ts
class RedisStore implements RateLimitStore
```

**Parameters**

| Name          | Type                 | Required | Default | Description             |
| ------------- | -------------------- | -------- | ------- | ----------------------- |
| `redisClient` | `RedisWithRateLimit` | Yes      | —       | ioredis client instance |
| `keyPrefix`   | `string`             | No       | `"rl:"` | Prefix for Redis keys   |

#### getClientIp

Extracts the client IP from request headers. Checks `x-forwarded-for`, `x-real-ip`, then falls back to `remoteAddress`.

```ts
function getClientIp(
  headers: Record<string, string | string[] | undefined>,
  remoteAddress?: string
): string;
```

#### RateLimitConfig

| Property          | Type               | Required | Description                    |
| ----------------- | ------------------ | -------- | ------------------------------ |
| `windowMs`        | `number`           | Yes      | Time window in milliseconds    |
| `max`             | `number`           | Yes      | Maximum requests allowed       |
| `statusCode`      | `number`           | Yes      | HTTP status when blocked       |
| `message`         | `string \| Record` | Yes      | Response body when blocked     |
| `standardHeaders` | `boolean`          | Yes      | Emit RFC `RateLimit-*` headers |
| `legacyHeaders`   | `boolean`          | Yes      | Emit `X-RateLimit-*` headers   |

#### RateLimitStore

```ts
interface RateLimitStore {
  increment(key: string, windowMs: number): Promise<RateLimitRecord> | RateLimitRecord;
}
```

#### RateLimitRecord

```ts
interface RateLimitRecord {
  hits: number;
  resetTime: number; // Unix timestamp in ms
}
```

#### RateLimitResult

```ts
interface RateLimitResult {
  isBlocked: boolean;
  statusCode: number;
  message: string | Record<string, unknown>;
  headers: Record<string, string>;
}
```

### Custom Key Generator

```ts
expressRateLimit({
  max: 100,
  windowMs: 60_000,
  store: new MemoryStore(),
  keyGenerator(req) {
    return req.user.id;
  }
});
```

### Custom Store

```ts
import { RateLimitStore, RateLimitRecord } from "@/blocks/rate-limiter/core/core";

class CustomStore implements RateLimitStore {
  async increment(key: string, windowMs: number): Promise<RateLimitRecord> {
    return { hits: 1, resetTime: Date.now() + windowMs };
  }
}
```

## FAQ

**What happens when the store throws an error?**

The adapter logs the error and calls `next()` (or `await next()`), allowing the request to proceed. This fail-open behavior prevents a store outage from taking down your API.

**How does the core engine compute headers?**

When `hits > config.max`, the result is marked as blocked and `Retry-After` is set to the remaining seconds in the window. Standard headers use delta seconds for `RateLimit-Reset`; legacy headers use an absolute Unix epoch timestamp.

**Can I use both standard and legacy headers?**

Yes. Both are enabled by default. Toggle them independently with `standardHeaders` and `legacyHeaders`.
