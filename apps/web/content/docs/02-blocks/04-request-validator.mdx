The request validator parses `body`, `query`, and `params` with Zod. It replaces the request values with the parsed result, applies defaults and coercion, and rejects invalid input before your route runs.

The block has no root `index.ts`. Import adapters from `adapters/` and the shared types from `contract`.

## Quick start

```bash
pnpm dlx blockend-cli init
pnpm dlx blockend-cli add request-validator
```

```ts
import express from "express";
import { z } from "zod";
import { expressValidator } from "@/blocks/request-validator/adapters/express";

const app = express();
app.use(express.json());

const validateUser = expressValidator({
  body: z.object({
    email: z.string().email()
  })
});

app.post("/users", validateUser, (req, res) => {
  const { body } = validateUser.validated(req);
  res.json({ email: body.email });
});
```

Register `express.json()` before the validator. Without a body parser, `req.body` is `undefined` and the schema fails.

## Configuration

The adapter takes a schema object and an options object:

```ts
{
  body?: z.ZodTypeAny;
  query?: z.ZodTypeAny;
  params?: z.ZodTypeAny;
}
```

```ts
{
  propagateErrors?: boolean; // default false
}
```

Parts you omit are not validated. They are parsed with `z.any()`, which accepts any value. Hono still reads the body as JSON, so a non-JSON body becomes `undefined` when body validation is omitted.

| Option            | Default | Description                                                                      |
| ----------------- | ------- | -------------------------------------------------------------------------------- |
| `propagateErrors` | `false` | Send the `ZodError` to your error handler instead of returning the built-in 400. |

## Usage

### Express

```ts
import { z } from "zod";
import { expressValidator } from "@/blocks/request-validator/adapters/express";

const validator = expressValidator({
  body: z.object({
    name: z.string().min(1),
    email: z.string().email()
  }),
  query: z.object({
    page: z.coerce.number().int().min(1).default(1)
  }),
  params: z.object({
    id: z.string().uuid()
  })
});

app.post("/users/:id", validator, (req, res) => {
  const { body, query, params } = validator.validated(req);
  res.json({ body, query, params });
});
```

The middleware replaces `req.body`, `req.query`, and `req.params` with parsed values. `validator.validated(req)` returns the same values with their inferred types.

`validated` throws if the middleware did not run for the request. Keep the middleware on the route or mount it before the handler.

### Fastify

```ts
import { z } from "zod";
import { fastifyValidator } from "@/blocks/request-validator/adapters/fastify";

const validator = fastifyValidator({
  body: z.object({
    name: z.string(),
    age: z.coerce.number()
  })
});

app.post("/users", { preHandler: validator }, async (request) => {
  const { body } = validator.validated(request);
  return body;
});
```

### Hono

```ts
import { Hono } from "hono";
import { z } from "zod";
import { honoValidator, validated } from "@/blocks/request-validator/adapters/hono";

const app = new Hono();

const schema = {
  body: z.object({
    name: z.string()
  })
};

app.post("/users", honoValidator(schema), (c) => {
  const { body } = validated<typeof schema.body, z.ZodTypeAny, z.ZodTypeAny>(c);
  return c.json(body);
});
```

Hono does not attach a `validated` method to the middleware. Use the exported `validated(c)` helper. The generic arguments are optional, but without them the result is not strongly typed.

## Error responses

With `propagateErrors: false`, a Zod failure returns status 400:

```json
{
  "success": false,
  "data": null,
  "message": "Validation failed",
  "errors": {
    "email": ["Invalid email"]
  }
}
```

The `errors` object contains field errors from `z.flattenError`. Nested schema errors may need your own formatter if you want a different shape.

With `propagateErrors: true`, the adapter passes the original `ZodError` to the framework error path. Use the error handler block's classifier to turn it into a 400 response:

```ts
import { z, ZodError } from "zod";
import { createErrorBoundary } from "@/blocks/error-handler";
import { createExpressErrorHandler } from "@/blocks/error-handler/adapters/express";

const boundary = createErrorBoundary({
  classifier(error) {
    if (!(error instanceof ZodError)) return null;

    return {
      code: "VALIDATION_FAILED",
      message: "Validation failed",
      statusCode: 400,
      category: "VALIDATION",
      details: z.treeifyError(error)
    };
  }
});

app.use(createExpressErrorHandler(boundary));
```

## Behavior

- Every schema is parsed with `schema.parse`, so transforms and defaults run.
- Validation runs before the route handler. Invalid input never reaches your business logic.
- Express replaces `req.query` and `req.params` with parsed values. Fastify assigns them directly. Hono stores the parsed values in its context.
- A non-Zod error thrown by a schema or transform is forwarded to the framework error path.
- The Express and Fastify adapters export `VALIDATED_KEY` if you need the internal symbol. Most code should use `validated()`.

## API reference

### `expressValidator`

```ts
function expressValidator(
  schemas: RequestValidationSchema,
  options?: { propagateErrors?: boolean }
): RequestHandler & {
  validated(req: Request): ValidatedData;
};
```

### `fastifyValidator`

```ts
function fastifyValidator(
  schemas: RequestValidationSchema,
  options?: { propagateErrors?: boolean }
): {
  (request: FastifyRequest, reply: FastifyReply): Promise<void>;
  validated(request: FastifyRequest): ValidatedData;
};
```

### `honoValidator`

```ts
function honoValidator(
  schemas: RequestValidationSchema,
  options?: { propagateErrors?: boolean }
): MiddlewareHandler;
```

### `validated`

```ts
function validated<TBody, TQuery, TParams>(c: Context): ValidatedData;
```

Reads the parsed values stored by `honoValidator`. Throws if the middleware has not run.

### `coreValidator`

```ts
function coreValidator<TSchema extends z.ZodTypeAny>(
  schema: TSchema,
  data: unknown
): z.infer<TSchema>;
```

A thin wrapper around `schema.parse` for custom adapters.

## Production notes

- Validate at the edge of the request. Do not repeat the same schema in the route.
- Keep schemas close to the route or in a shared module that both the route and tests import.
- Do not use `z.any()` for fields that affect authorization or billing.
- Treat parsed values as the source of truth. Avoid reading raw `req.body` after validation.
- Zod strips unknown keys by default on object schemas. If you need to reject unknown keys, use `.strict()`.

## When not to use it

- You already use a schema-first framework that validates at the route boundary.
- You need OpenAPI generation from the same schema. This block does not generate specs.
- You need validation outside HTTP requests. Use Zod directly.
