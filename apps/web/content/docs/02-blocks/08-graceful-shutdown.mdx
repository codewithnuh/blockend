The graceful shutdown block coordinates process shutdown. It stops accepting new work, waits for active requests to finish, runs cleanup tasks from highest priority to lowest, and enforces a hard timeout.

The root `index.ts` exports the core and constants. Framework adapters live in `adapters/`.

## Quick start

```bash
pnpm dlx blockend-cli init
pnpm dlx blockend-cli add graceful-shutdown
```

```ts
import { createServer } from "node:http";
import express from "express";
import { GracefulShutdown, PRIORITY } from "@/blocks/graceful-shutdown";
import {
  createExpressShutdownTask,
  createExpressTracker,
  createShutdownMiddleware
} from "@/blocks/graceful-shutdown/adapters/express";

const app = express();
const server = createServer(app);

const tracker = createExpressTracker(server);
const shutdown = new GracefulShutdown({
  connectionTracker: tracker,
  drainTimeoutMs: 10_000,
  hardTimeoutMs: 30_000
});

// Register this before routes so new requests get 503 during shutdown.
app.use(createShutdownMiddleware(shutdown));

app.get("/api/slow", async (_req, res) => {
  await sleep(2_000);
  res.json({ ok: true });
});

// The server task is required. The tracker does not close the listener.
shutdown.addTask(createExpressShutdownTask(server));

shutdown.addTask({
  name: "db-pool",
  priority: PRIORITY.DB_POOL,
  handler: () => db.end()
});

server.listen(3000);
```

On `SIGTERM`, the order is:

1. `isShuttingDownState` becomes `true`. The middleware returns 503 for new requests.
2. The tracker waits for in-flight requests, up to `drainTimeoutMs`.
3. The server task closes the listener.
4. The database task closes the pool.
5. The process exits with code 0 if no task failed, otherwise code 1.

## Configuration

```ts
const shutdown = new GracefulShutdown({
  hardTimeoutMs: 30_000,
  defaultTaskTimeoutMs: 10_000,
  drainTimeoutMs: 10_000,
  stopOnError: false,
  installSignalHandlers: true,
  connectionTracker: tracker,
  onTaskComplete(name, durationMs, error) {
    metrics.observe("shutdown_task_seconds", durationMs / 1000, { name });
  }
});
```

| Option                  | Default | Description                                                   |
| ----------------------- | ------- | ------------------------------------------------------------- |
| `hardTimeoutMs`         | `30000` | Forced `process.exit(1)` after this long. Cannot be disabled. |
| `defaultTaskTimeoutMs`  | `10000` | Timeout for tasks without their own `timeout`.                |
| `drainTimeoutMs`        | `10000` | How long to wait for active requests before running tasks.    |
| `stopOnError`           | `false` | Stop running tasks after the first failure.                   |
| `installSignalHandlers` | `true`  | Listen for `SIGTERM`, `SIGINT`, and `SIGQUIT`.                |
| `connectionTracker`     | None    | Waits for active requests before tasks run.                   |
| `onTaskComplete`        | None    | Called with `name`, `durationMs`, and an optional error.      |

Signal handlers call `shutdown(reason)` and exit. If a second signal arrives during shutdown, the process exits immediately.

`uncaughtException` and `unhandledRejection` are not handled. Wire those in your entry point and call `shutdown.shutdown("uncaughtException")` yourself.

## Tasks

A task has a name, a handler, an optional timeout, and an optional priority:

```ts
shutdown.addTask({
  name: "cache",
  priority: PRIORITY.CACHE,
  timeout: 5_000,
  handler: async () => {
    await redis.quit();
  }
});
```

Higher priority runs first. Tasks with the same name replace each other. `addTask` returns the manager, so calls can chain.

| Priority         | Value | Use for                      |
| ---------------- | ----- | ---------------------------- |
| `HTTP_SERVER`    | 100   | Stop accepting requests      |
| `QUEUE_CONSUMER` | 80    | Stop consuming messages      |
| `JOB_QUEUE`      | 60    | Stop background workers      |
| `DB_POOL`        | 40    | Close database pools         |
| `CACHE`          | 20    | Close Redis and other caches |
| `LOGGERS`        | 10    | Flush logs last              |

The default priority is 50. A task that times out counts as failed and the next task still runs unless `stopOnError` is true. A timed-out task is not canceled; its handler can keep running while the next task starts.

If you add a task after shutdown starts, it runs immediately and is not tracked in the result.

### The server task is required

The connection tracker only counts requests. It does not close the listening socket. Add the framework's server task:

```ts
shutdown.addTask(createExpressShutdownTask(server));
shutdown.addTask(createFastifyShutdownTask(app));
shutdown.addTask(createHonoShutdownTask(server));
```

Without it, shutdown never closes the listening socket. With signal handlers enabled, the process exits after the remaining tasks finish. If you call `shutdown()` yourself, close the server after it resolves or call `process.exit`.

## Usage

### Express

```ts
import { createServer } from "node:http";
import express from "express";
import { GracefulShutdown, PRIORITY } from "@/blocks/graceful-shutdown";
import {
  createExpressShutdownTask,
  createExpressTracker,
  createShutdownMiddleware
} from "@/blocks/graceful-shutdown/adapters/express";

const app = express();
const server = createServer(app);
const tracker = createExpressTracker(server);
const shutdown = new GracefulShutdown({ connectionTracker: tracker });

app.use(createShutdownMiddleware(shutdown));

app.get("/health", (_req, res) => {
  res.json({ status: "ok" });
});

shutdown.addTask(createExpressShutdownTask(server));
shutdown.addTask({
  name: "db",
  priority: PRIORITY.DB_POOL,
  handler: () => db.end()
});

server.listen(3000);
```

Create the server with `createServer(app)` before `listen()` so the tracker can attach early. The middleware must be registered before routes.

### Fastify

```ts
import Fastify from "fastify";
import { GracefulShutdown } from "@/blocks/graceful-shutdown";
import {
  createFastifyShutdownTask,
  createFastifyTracker,
  registerFastifyShutdownHooks
} from "@/blocks/graceful-shutdown/adapters/fastify";

const app = Fastify();
const tracker = createFastifyTracker(app);
const shutdown = new GracefulShutdown({ connectionTracker: tracker });

registerFastifyShutdownHooks(app, shutdown);
app.get("/health", async () => {
  return { status: "ok" };
});

shutdown.addTask(createFastifyShutdownTask(app));

await app.listen({ port: 3000 });
```

`registerFastifyShutdownHooks` adds an `onRequest` hook and must be called before `listen()`. The Fastify task calls `fastify.close()`, which runs `onClose` hooks.

### Hono on Node

```ts
import { createServer } from "node:http";
import { getRequestListener } from "@hono/node-server";
import { Hono } from "hono";
import { GracefulShutdown } from "@/blocks/graceful-shutdown";
import {
  createHonoShutdownMiddleware,
  createHonoShutdownTask,
  createHonoTracker
} from "@/blocks/graceful-shutdown/adapters/hono";

const app = new Hono();
const server = createServer(getRequestListener(app.fetch));
const tracker = createHonoTracker(server);
const shutdown = new GracefulShutdown({ connectionTracker: tracker });

app.use("*", createHonoShutdownMiddleware(shutdown));

app.get("/health", (c) => {
  return c.json({ status: "ok" });
});

shutdown.addTask(createHonoShutdownTask(server));

server.listen(3000);
```

## Events

```ts
shutdown.on("beforeShutdown", (reason) => {
  console.log("Shutdown started", reason);
});

shutdown.on("draining", () => {
  console.log("Waiting for active requests");
});

shutdown.on("drained", () => {
  console.log("Active requests finished");
});

shutdown.on("drainTimeout", () => {
  console.warn("Drain timed out, running tasks anyway");
});

shutdown.on("afterShutdown", (result) => {
  console.log(result.success, result.completed, result.failed);
});
```

`drainTimeout` fires when the tracker does not reach zero in time. Tasks still run.

## API reference

### `GracefulShutdown`

```ts
class GracefulShutdown {
  constructor(options?: GracefulShutdownOptions);

  readonly isShuttingDownState: boolean;

  addTask(task: ShutdownTask): this;
  removeTask(name: string): boolean;
  getTaskNames(): string[];

  shutdown(reason?: ShutdownReason): Promise<ShutdownResult>;

  on(event: "beforeShutdown", listener: (reason: ShutdownReason) => void): this;
  on(event: "draining" | "drained" | "drainTimeout", listener: () => void): this;
  on(event: "afterShutdown", listener: (result: ShutdownResult) => void): this;
}
```

`shutdown()` is idempotent. Every caller gets the same promise. The first call sets `isShuttingDownState` to true.

### `ShutdownResult`

```ts
interface ShutdownResult {
  success: boolean;
  completed: string[];
  failed: Array<{ name: string; error: Error }>;
  durationMs: number;
}
```

### `ShutdownTask`

```ts
interface ShutdownTask {
  name: string;
  handler: () => Promise<void> | void;
  timeout?: number;
  priority?: number;
}
```

### `NodeConnectionTracker`

```ts
class NodeConnectionTracker {
  attach(server: Server): this;
  detach?(): void;
  readonly activeCount: number;
  waitForDrain(timeoutMs: number): Promise<void>;
}
```

The tracker counts requests that have started and not finished. It listens to the Node HTTP server's request, finish, and close events.

### Utility exports

The root also exports:

- `createHttpShutdownTask(server, options?)`
- `gracefulShutdown`, a lazily created singleton
- `handleNode503`
- `shouldRejectRequest`
- `withTimeout`
- `isAttachable`

Prefer `new GracefulShutdown()` over the singleton in tests and multi-tenant workers. The singleton is created on first use so importing the module does not install signal handlers.

## Production notes

- Set `hardTimeoutMs` below your platform's stop timeout. Kubernetes `terminationGracePeriodSeconds` and Docker's `--stop-timeout` should leave room for the forced exit.
- Register the shutdown middleware before routes so draining instances do not accept new work.
- Keep the liveness probe independent of dependencies. The shutdown middleware returns 503 for new requests, including liveness, once shutdown starts. With Express or Hono, you can register the liveness route before the middleware to keep it at 200. The Fastify hook is global, so leave the hook out or add an explicit exemption if liveness must stay at 200.
- Use a drain timeout shorter than the hard timeout. With the defaults, the drain can take 10 seconds and the HTTP close task can take 15 seconds, leaving room inside 30 seconds. Each additional task can consume its own timeout, so budget the sum of task timeouts as well.
- Do not close the database before in-flight requests finish. The tracker drains first, then tasks run.
- Flush logs last, after the resources that may write logs.
- Run tests with `installSignalHandlers: false` so the test process does not exit.

## When not to use it

- Serverless functions with no long-lived process. The platform controls the lifecycle.
- Short-lived scripts that do not own a listening socket or shared resources.
- Apps that already use a shutdown coordinator and cannot register another signal handler.
