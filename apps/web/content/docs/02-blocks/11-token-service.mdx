The token service issues short-lived JWT access tokens and single-use refresh tokens. It verifies signatures, issuer, audience, expiry, token type, and an optional JTI denylist before returning access claims.

Your app still authenticates users, stores credentials, manages cookies and CSRF, and decides authorization. This block handles token mechanics and refresh rotation.

<Callout type="warn">
  `MemoryTokenStore` is process-local and loses state on restart. Use PostgreSQL or Redis for
  refresh tokens in a multi-instance deployment. Use `StatelessTokenStore` only for
  access-token-only services that do not need refresh or server-side revocation.
</Callout>

## Quick start

```bash
pnpm dlx blockend-cli init
pnpm dlx blockend-cli add token-service
```

This example creates a temporary RSA key, issues one access token, and verifies it:

```ts
import { generateKeyPairSync } from "node:crypto";
import {
  createTokenService,
  LocalKeyProvider,
  StatelessTokenStore
} from "@/blocks/token-service/src";

const { privateKey, publicKey } = generateKeyPairSync("rsa", {
  modulusLength: 2048
});

const tokens = createTokenService({
  deploymentMode: "development",
  issuer: "http://localhost:3000",
  algorithms: ["RS256"],
  keyProvider: new LocalKeyProvider({
    signingKid: "local-dev",
    keys: [
      {
        kid: "local-dev",
        alg: "RS256",
        privateKeyPem: privateKey.export({ type: "pkcs8", format: "pem" }).toString(),
        publicKeyPem: publicKey.export({ type: "spki", format: "pem" }).toString()
      }
    ]
  }),
  tokenStore: new StatelessTokenStore()
});

const pair = await tokens.issue({
  sub: "user-123",
  tokens: { access: true, refresh: false }
});

const result = await tokens.verify(pair.accessToken!);

console.log(result.claims.sub); // "user-123"
```

The example generates new keys on every start, so tokens from an earlier run will not verify. It also has no refresh or revocation state. Continue to [Production setup](#production-setup) for a persistent store.

## Configuration

```ts
const tokens = createTokenService({
  issuer: "https://auth.example.com",
  audience: ["https://api.example.com"],
  keyProvider,
  tokenStore,
  accessTokenTtlSeconds: 900,
  refreshTokenTtlSeconds: 604_800
});
```

| Option                            | Default                | Description                                                           |
| --------------------------------- | ---------------------- | --------------------------------------------------------------------- |
| `deploymentMode`                  | `"production"`         | Development allows localhost HTTP and omits the audience requirement. |
| `issuer`                          | Required               | Production requires an `https://` URL or a `urn:`.                    |
| `audience`                        | Required in production | Allowed audience values.                                              |
| `accessTokenTtlSeconds`           | `900`                  | Clamped to 60 through 3600.                                           |
| `refreshTokenTtlSeconds`          | `604800`               | Clamped to 3600 through 2,592,000.                                    |
| `maxRefreshFamilyLifetimeSeconds` | `7776000`              | Absolute family lifetime, 3600 through 31,536,000.                    |
| `maxRefreshRotations`             | `10000`                | Successful rotations per family, 1 through 1,000,000.                 |
| `clockSkewSeconds`                | `30`                   | JWT clock tolerance, 0 through 300.                                   |
| `algorithms`                      | `["RS256", "ES256"]`   | Signing algorithms. Production rejects `HS*`.                         |
| `maxClaimsBytes`                  | `4096`                 | Custom claim size limit, 256 through 16,384 bytes.                    |
| `forbiddenClaimKeys`              | Built-in list          | Replaces the default forbidden claim list.                            |
| `keyProvider`                     | Required               | Signing and verification keys.                                        |
| `tokenStore`                      | Required               | Refresh and revocation state.                                         |
| `onEvent`                         | None                   | Receives token lifecycle events. Throwing from it is ignored.         |
| `resolveRefreshContext`           | None                   | Reloads current claims and audience during refresh.                   |
| `now`                             | `() => new Date()`     | Clock injection for tests.                                            |

`createTokenService` validates the options immediately. Invalid options throw `TokenError` with code `INVALID_INPUT`.

### Issue input

| Field                    | Default         | Description                                                    |
| ------------------------ | --------------- | -------------------------------------------------------------- |
| `sub`                    | Required        | Trimmed subject, 1 to 512 characters.                          |
| `claims`                 | `{}`            | Custom JSON claims. Reserved and forbidden names are rejected. |
| `tokens.access`          | `true`          | Issue an access token.                                         |
| `tokens.refresh`         | `true`          | Issue a refresh token. At least one token must be requested.   |
| `accessTokenTtlSeconds`  | Service setting | Per-token access lifetime, clamped to 60 through 3600.         |
| `refreshTokenTtlSeconds` | Service setting | Per-token refresh lifetime, clamped to 3600 through 2,592,000. |
| `audience`               | Service setting | Must be contained in the configured audience.                  |

## Usage

### Production setup

Apply `token-service/sql/postgres.sql` before using `PostgresTokenStore`. Provide a `PgLike` implementation whose `transaction()` runs every callback query on one connection:

```ts
import {
  createTokenService,
  LocalKeyProvider,
  PostgresTokenStore
} from "@/blocks/token-service/src";
import { database } from "./database";

export const tokens = createTokenService({
  issuer: "https://auth.example.com",
  audience: ["https://api.example.com"],
  algorithms: ["RS256"],
  accessTokenTtlSeconds: 600,
  keyProvider: new LocalKeyProvider({
    signingKid: "rsa-2026-09",
    keys: [
      {
        kid: "rsa-2026-09",
        alg: "RS256",
        privateKeyPem: process.env.JWT_PRIVATE_KEY_PEM!,
        publicKeyPem: process.env.JWT_PUBLIC_KEY_PEM!
      }
    ]
  }),
  tokenStore: new PostgresTokenStore(database),
  resolveRefreshContext: async (sub) => {
    const user = await database.users.findAuthorizationContext(sub);

    if (!user || user.disabled) {
      throw new Error("User is unavailable");
    }

    return {
      claims: {
        role: user.role,
        permissions: user.permissions
      }
    };
  }
});
```

The transaction wrapper must check out one client, run `BEGIN`, commit on success, and roll back on error. The store does not manage a pool.

For Redis, pass a client implementing `get`, `hget`, `set`, and `eval`. `ioredis` needs a small adapter. Use a stable base64url-encoded subject routing key with at least 32 decoded bytes:

```ts
import { Redis } from "ioredis";
import { RedisTokenStore, type RedisLike } from "@/blocks/token-service/src";

const redis = new Redis(process.env.REDIS_URL!);

const redisAdapter: RedisLike = {
  get: (key) => redis.get(key),
  hget: (key, field) => redis.hget(key, field),
  set: (key, value, options) => {
    if (options?.PX !== undefined && options.NX) {
      return redis.set(key, value, "PX", options.PX, "NX");
    }
    if (options?.PX !== undefined) return redis.set(key, value, "PX", options.PX);
    if (options?.NX) return redis.set(key, value, "NX");
    return redis.set(key, value);
  },
  eval: (script, input) => redis.eval(script, input.keys.length, ...input.keys, ...input.arguments)
};

const redisStore = new RedisTokenStore(redisAdapter, {
  prefix: "company-auth:v2:",
  subjectRoutingKey: Buffer.from(process.env.TOKEN_REDIS_SUBJECT_KEY!, "base64url")
});
```

Keep the routing key and prefix identical on every instance. Do not rotate the routing key until every family created with it has expired or been revoked.

<Callout type="warn">
  Run Redis token state with `maxmemory-policy noeviction` in a dedicated deployment. Redis must
  reject writes instead of evicting family or JTI state. Redis Cluster replication is asynchronous
  and can lose acknowledged writes during failover. Use PostgreSQL if revocation durability across
  failover is a hard requirement.
</Callout>

import express from "express";

Mount the route group behind your authentication and request size middleware. The examples assume your auth layer sets `request.auth` on Express, decorates `request.user` on Fastify, and sets the `service` variable in Hono.

## How refresh works

A refresh request:

1. Parses the family hint from the opaque refresh token.
2. Hashes the token and looks up the record.
3. Reloads current claims with `resolveRefreshContext` when configured.
4. Signs a new access token before consuming the old refresh token.
5. Atomically marks the old hash used and stores the replacement.
6. Revokes the whole family if an already-used token appears again.

A refresh token is an opaque credential, not a JWT. It is 32 to 512 characters and contains a family routing hint plus a random secret. The store keeps only a SHA-256 hash.

The refresh token lifetime is clamped to the family deadline. A family also has a rotation ceiling. Reaching either limit returns `TOKEN_EXPIRED` or `REFRESH_LIMIT`.

If `resolveRefreshContext` throws, the old refresh token is not consumed, so the client can retry. Keep that callback fast and reliable.

## Key rotation

Keep old public keys in the provider while access tokens signed with them can still verify:

```ts
const provider = new LocalKeyProvider({
  signingKid: "rsa-2026-10",
  keys: [
    { kid: "rsa-2026-10", alg: "RS256", privateKeyPem: newPem, publicKeyPem: newPub },
    { kid: "rsa-2026-09", alg: "RS256", privateKeyPem: oldPem, publicKeyPem: oldPub }
  ]
});
```

Switch `signingKid` to the new key, wait at least the maximum access token lifetime plus clock skew, then remove the old key. For a remote JWKS provider, publish the new public key before signing with it.

`LocalKeyProvider` requires a `kid` on every token it verifies. Keys must have unique IDs. `KmsRsaKeyProvider` signs RS256 through an external function but does not hold private key material.

## HTTP routes

The adapters mount refresh by default. Issue, verify, and revoke are opt-in.

| Route           | Default  | Authorization                 | Success                   |
| --------------- | -------- | ----------------------------- | ------------------------- |
| `POST /refresh` | Enabled  | Application policy            | Rotated token pair        |
| `POST /issue`   | Disabled | `authorize` callback required | Token pair                |
| `POST /verify`  | Disabled | Application policy            | `{ valid: true, claims }` |
| `POST /revoke`  | Disabled | `authorize` callback required | `{ revoked: true }`       |

A missing or denied authorization callback returns 403. Errors use `{ error: { code, message } }`.

| Error type                                        | Status |
| ------------------------------------------------- | ------ |
| Invalid input, oversized claims, forbidden claims | 400    |
| Invalid, expired, revoked, or reused token        | 401    |
| Store or key unavailable                          | 503    |
| Unsupported operation                             | 501    |

The adapters do not add authentication, CSRF, CORS, or rate limiting. Set a body size limit before mounting them. Exposing `/issue` without an authorization check lets callers mint tokens.

## API reference

### `createTokenService`

```ts
function createTokenService(options: TokenServiceOptions): TokenService;
```

### `TokenService`

```ts
interface TokenService {
  issue(input: IssueInput): Promise<TokenPair>;
  verify(accessToken: string): Promise<VerifyResult>;
  refresh(refreshToken: string): Promise<TokenPair>;
  revoke(input: RevokeInput): Promise<void>;
}
```

`verify` accepts access tokens only. Refresh tokens cannot be used as access tokens.

### Result types

```ts
interface TokenPair {
  accessToken?: string;
  refreshToken?: string;
  tokenType: "Bearer";
  expiresIn?: number;
  refreshExpiresIn?: number;
  issuedAt: number;
}

interface AccessTokenClaims {
  sub: string;
  iss: string;
  aud?: string | string[];
  exp: number;
  iat: number;
  jti: string;
  type: "access";
  [key: string]: unknown;
}

interface VerifyResult {
  valid: true;
  claims: AccessTokenClaims;
}

type RevokeInput =
  | { refreshToken: string }
  | { jti: string }
  | { sub: string }
  | { familyId: string };
```

Revoke accepts exactly one target. Revoking a refresh token revokes its whole family. Revoking an access token requires a store that implements `revokeByJti` and `isJtiRevoked`; verification checks the denylist when they are present.

### Store contract

A `TokenStore` implements:

```ts
interface TokenStore {
  createFamilyId?(sub: string): string;
  saveRefreshToken(record: RefreshTokenRecord): Promise<void>;
  getRefreshToken(tokenHash: string, familyId?: string): Promise<RefreshTokenRecord | undefined>;
  rotateRefreshToken(input: {
    currentHash: string;
    replacement: RefreshTokenRecord;
    now: Date;
    maxRotations: number;
  }): Promise<RotateResult>;
  revokeByHash(tokenHash: string, familyId?: string): Promise<void>;
  revokeByFamily(familyId: string): Promise<void>;
  revokeBySub(sub: string): Promise<void>;
  revokeByJti?(jti: string, expiresAt?: Date): Promise<void>;
  isJtiRevoked?(jti: string): Promise<boolean>;
}
```

Rotation and family revocation must be atomic across every app instance. `MemoryTokenStore` is for tests and single-process development. `StatelessTokenStore` supports access tokens only and throws `UNSUPPORTED_OPERATION` for refresh and server-side revoke.

`RedisTokenStoreOptions` requires `subjectRoutingKey` and accepts an optional `prefix`. The default prefix is `blockend:v2:`. `PostgresTokenStore` requires `PgLike` with `query()` and `transaction()`. The transaction callback receives a `PgTransaction` with `query()`.

## Events and errors

Events are `token.issued`, `token.verified`, `token.refreshed`, `token.revoked`, `token.reuse_detected`, and `token.failed`. Each has an ISO timestamp and optional subject, JTI, family ID, or error code. Raw tokens are never included.

| Code                    | Meaning                                                           |
| ----------------------- | ----------------------------------------------------------------- |
| `INVALID_INPUT`         | Configuration or operation input failed validation.               |
| `INVALID_TOKEN`         | Malformed token or issuer, audience, algorithm, or type mismatch. |
| `TOKEN_EXPIRED`         | Access token, refresh token, or refresh family expired.           |
| `TOKEN_REVOKED`         | Refresh token or access JTI is revoked.                           |
| `REFRESH_REUSED`        | A used refresh token appeared again; its family was revoked.      |
| `REFRESH_LIMIT`         | The family reached its rotation ceiling.                          |
| `CLAIMS_TOO_LARGE`      | Custom claims exceed `maxClaimsBytes`.                            |
| `FORBIDDEN_CLAIM`       | Custom claims contain a reserved or forbidden name.               |
| `KEY_UNAVAILABLE`       | A signing or verification key could not be used.                  |
| `STORE_UNAVAILABLE`     | A store operation failed.                                         |
| `UNSUPPORTED_OPERATION` | The selected store does not support the operation.                |

## Testing your integration

Use `MemoryTokenStore` and a fixed key pair in tests. Inject `now` when you need deterministic expiry:

```ts
import { createTokenService, LocalKeyProvider, MemoryTokenStore } from "@/blocks/token-service/src";

let now = new Date("2026-01-01T00:00:00Z");

const tokens = createTokenService({
  deploymentMode: "development",
  issuer: "http://localhost:3000",
  audience: "test-api",
  keyProvider: new LocalKeyProvider({
    signingKid: "test",
    keys: [{ kid: "test", alg: "RS256", privateKeyPem, publicKeyPem }]
  }),
  tokenStore: new MemoryTokenStore(),
  now: () => now
});
```

Test these cases:

- A valid access token verifies and returns the subject and claims.
- A token with the wrong audience or issuer is rejected.
- An expired access token returns `TOKEN_EXPIRED`.
- Refresh rotates the token; reusing the old token returns `REFRESH_REUSED` and revokes the family.
- Rotating past `maxRefreshRotations` returns `REFRESH_LIMIT`.
- Revoking a subject invalidates its refresh families.
- A custom store's rotation is atomic under concurrent requests.

Run these tests against the same database or Redis engine you use in production. In-memory behavior can hide transaction and concurrency bugs.

## When not to use it

- You need a complete identity provider, login UI, OAuth/OIDC server, account recovery, or authorization policy.
- You need refresh state that survives restarts but can only use `MemoryTokenStore`.
- You need multi-region refresh consistency without a strongly consistent shared store.
- You need access tokens without a server, such as a static client. There is no secure place to keep a signing key.
