The idempotency block wraps a state-changing operation so that retries with the same key return the stored result instead of running the operation again.

A request is scoped by `(userId, operation, idempotency key)`. The first request creates a `PROCESSING` record. Later requests either replay the stored success, receive a conflict because the first request is still running, or receive a conflict because it failed.

The block does not include a database store or cache. You provide an `IdempotencyStore`. A cache is optional.

<Callout type="warn">
  Set `getUserId` to a real authenticated user ID. The default falls back to `"anonymous"` when the
  framework request has no user, which gives every caller the same key scope. A client that learns a
  key and payload could then read another user's stored response.
</Callout>

## Quick start

```bash
pnpm dlx blockend-cli init
pnpm dlx blockend-cli add idempotency
```

```ts
import express from "express";
import { IdempotencyHandler } from "@/blocks/idempotency";
import { idempotent } from "@/blocks/idempotency/adapters/express";

const app = express();
app.use(express.json());

// Your store implements IdempotencyStore.
const handler = new IdempotencyHandler(store);

app.post(
  "/payments",
  idempotent(
    handler,
    async (req) => {
      const charge = await createCharge(req.body);
      return { id: charge.id, status: charge.status };
    },
    {
      requireKey: true,
      getUserId: (req) => req.user.id,
      getOperation: () => "payments:create"
    }
  )
);
```

Register authentication before this route. `req.user.id` must be set by trusted middleware. The examples assume your auth layer declares `req.user` on the Express request type.

## Store contract

Your `IdempotencyStore` is the source of truth. It must implement:

```ts
interface IdempotencyStore {
  create(record: IdempotencyRecord): Promise<CreateRecordResult>;
  find(key: string, operation: string, userId: string): Promise<IdempotencyRecord | null>;
  findAll(filters?: FindAllFilters): Promise<IdempotencyRecord[]>;
  markSuccess(key: string, response: unknown, userId: string, operation: string): Promise<void>;
  markProcessing(key: string, operation: string, userId: string): Promise<void>;
  markFailed(key: string, operation: string, userId: string): Promise<void>;
  incrementRetryCount(key: string, operation: string, userId: string): Promise<number>;
  delete(key: string, operation: string, userId: string): Promise<void>;
  deleteExpired(params: DeleteExpiredParams): Promise<number>;
}
```

Requirements that the block depends on:

1. `create` must be atomic. Use a unique constraint on `(operation, userId, key)` or an equivalent compare-and-set. If two inserts can both return `CREATED`, both requests will run your business logic.
2. `incrementRetryCount` must survive record deletion. After a transient failure the handler deletes the row so the client can retry. If the counter lives on that row, it resets and the key is never poisoned.
3. `markSuccess` and `markFailed` should only update a record that is still `PROCESSING`. Do not overwrite a completed success.
4. `deleteExpired` must only delete `SUCCESS` and `FAILED` records. Active `PROCESSING` locks are handled by the recovery job.
5. `find` must treat expired `SUCCESS` and `FAILED` records as absent, and `create` must be able to replace them. The handler does not check `expiresAt` before replaying a stored response. Do not hide or replace an expired `PROCESSING` record, because the original operation may still be running.
6. Storage must be shared by every app instance. A per-process map cannot deduplicate requests across replicas.

The `IdempotencyRecord` passed to `create` uses camelCase fields:

```ts
type IdempotencyRecord = {
  key: string;
  userId: string;
  operation: string;
  requestHash: string;
  status: "PROCESSING" | "SUCCESS" | "FAILED";
  response?: unknown;
  expiresAt: Date;
  createdAt: Date;
  updatedAt: Date;
};
```

Map those fields to your schema. The internal record TTL is 24 hours. It is not configurable.

## Configuration

### Handler

```ts
const handler = new IdempotencyHandler(store, cache?, options?);
```

| Argument  | Type               | Required | Description                                                 |
| --------- | ------------------ | -------- | ----------------------------------------------------------- |
| `store`   | `IdempotencyStore` | Yes      | Persistent, shared idempotency records.                     |
| `cache`   | `IdempotencyCache` | No       | Fast replay path. Falls back to the store when unavailable. |
| `logger`  | `Logger`           | No       | Pino-shaped logger. Defaults to a no-op logger.             |
| `metrics` | `Metrics`          | No       | Metrics sink. Defaults to a no-op sink.                     |

### Adapter options

Express, Fastify, and Hono use the same option names:

| Option             | Type                                            | Default                            | Description                                                   |
| ------------------ | ----------------------------------------------- | ---------------------------------- | ------------------------------------------------------------- |
| `key`              | `IdempotencyKeySource`                          | `Idempotency-Key` header           | Also supports `bodyField` and `queryParam`.                   |
| `requireKey`       | `boolean`                                       | `false`                            | Reject a missing key with 400 instead of running unprotected. |
| `getUserId`        | `(request) => string \| undefined`              | Framework user ID or `"anonymous"` | Scopes the key to a user.                                     |
| `getOperation`     | `(request) => string`                           | Method and path                    | Scopes the key to an operation.                               |
| `getBody`          | `(request) => unknown`                          | Request body or `{}`               | Payload hashed to detect key reuse with different input.      |
| `isPermanentError` | `(error) => boolean`                            | Every error is permanent           | Decides whether a failure poisons the key.                    |
| `attachContext`    | `boolean`                                       | `true`                             | Attaches request context for observability.                   |
| `statusMap`        | `Partial<Record<IdempotencyErrorCode, number>>` | Built-in map                       | Overrides HTTP status codes.                                  |

Fastify uses the registered route pattern for its default operation, so `/payments/:id` stays stable across IDs. Express and Hono use the concrete path by default. Set `getOperation` if you want identical behavior across frameworks.

The examples assume your auth layer declares `req.user` on Express, `request.user` on Fastify, and the `user` context variable on Hono.

### Key validation

`handler.validateKey(key)` trims the key, checks its length, and checks the allowed characters.

```ts
const key = handler.validateKey("  order_123  "); // "order_123"
```

The default minimum is 1 character, the maximum is 128, and the allowed characters are letters, numbers, `.`, `_`, `-`, and `:`. Pass `KeyValidationOptions` to require a UUID or change the limits:

```ts
const key = handler.validateKey(rawKey, {
  minLength: 16,
  maxLength: 64,
  requireUuid: true
});
```

Adapters call `handler.validateKey` with the defaults. If you need per-route validation options, validate the key before calling the adapter or use the core directly.

## Usage

### Express wrapper

Use `idempotent()` when the route returns its response payload. The adapter sends the returned value with `res.json`.

```ts
import { idempotent } from "@/blocks/idempotency/adapters/express";

app.post(
  "/payments",
  idempotent(
    handler,
    async (req) => {
      const charge = await createCharge(req.body);
      return { id: charge.id, status: charge.status };
    },
    {
      requireKey: true,
      getUserId: (req) => req.user.id,
      getOperation: () => "payments:create",
      isPermanentError: (error) => error instanceof ValidationError
    }
  )
);
```

### Express middleware

Use `idempotencyMiddleware()` when the route sends its own response with `res.json` or `res.send`.

```ts
import { idempotencyMiddleware } from "@/blocks/idempotency/adapters/express";

app.post(
  "/payments",
  idempotencyMiddleware(handler, {
    requireKey: true,
    getUserId: (req) => req.user.id
  }),
  async (req, res) => {
    const charge = await createCharge(req.body);
    res.status(201).json(charge);
  }
);
```

The middleware captures the body, but not the status code. A replay is sent with status 200. If clients depend on 201, return the status in the body or use a response shape that does not require the original status.

### Fastify

The Fastify wrapper supports both return-style and `reply.send()` routes.

```ts
import { idempotent } from "@/blocks/idempotency/adapters/fastify";

app.post(
  "/payments",
  idempotent(
    handler,
    async (request) => {
      const charge = await createCharge(request.body);
      return { id: charge.id, status: charge.status };
    },
    {
      requireKey: true,
      getUserId: (request) => request.user.id
    }
  )
);

app.post(
  "/refunds",
  idempotent(handler, async (request, reply) => {
    reply.code(201).send(await createRefund(request.body));
  })
);
```

As with Express, only the payload is stored. A replay uses the adapter's default 200 response.

### Hono

Hono has a wrapper and a capture middleware.

```ts
import { idempotent, idempotencyMiddleware } from "@/blocks/idempotency/adapters/hono";

app.post(
  "/payments",
  idempotent(
    handler,
    async (c) => {
      const charge = await createCharge(await c.req.json());
      return { id: charge.id, status: charge.status };
    },
    {
      requireKey: true,
      getUserId: (c) => c.get("user").id
    }
  )
);

app.post(
  "/refunds",
  idempotencyMiddleware(handler, {
    requireKey: true,
    getUserId: (c) => c.get("user").id
  }),
  async (c) => {
    const refund = await createRefund(await c.req.json());
    return c.json(refund, 201);
  }
);
```

The Hono middleware reads the request body from a clone, so the route can still call `c.req.json()`.

Return a plain payload from the Hono wrapper when you need replay. A `Response` object does not serialize to useful JSON in a persistent store.

### Core without an adapter

```ts
import { IdempotencyError, IdempotencyHandler } from "@/blocks/idempotency";
import { buildErrorEnvelope, idempotencyErrorStatus } from "@/blocks/idempotency/adapters/shared";

const handler = new IdempotencyHandler(store);

app.post("/payments", async (req, res, next) => {
  try {
    const key = handler.validateKey(req.get("Idempotency-Key"));
    const result = await handler.execute(
      req.user.id,
      "payments:create",
      key,
      req.body,
      () => createCharge(req.body),
      { isPermanentError: (error) => error instanceof ValidationError }
    );

    res.json(result);
  } catch (error) {
    if (error instanceof IdempotencyError) {
      res.status(idempotencyErrorStatus(error)).json(buildErrorEnvelope(error));
      return;
    }

    next(error);
  }
});
```

`validateKey` throws `KEY_INVALID_TYPE` for a missing or non-string value, and `KEY_REQUIRED` for an empty or whitespace-only string. Use an adapter with `requireKey: true` for the same behavior with less code.

## What gets stored

The block stores the return value of your route as JSON. It does not store the HTTP status code or response headers.

Return a value from wrapper-style routes. A stored `undefined` response leaves Fastify with nothing to send, and adapters differ in how they handle an empty replay.

The request body is hashed with a deterministic serializer. Values such as `undefined`, `NaN`, `Infinity`, `BigInt`, functions, and symbols cannot be serialized and will fail. The adapters use `{}` when the request has no body, so a missing body hashes as an empty object. Pass only JSON-compatible data, or provide `getBody` that returns a stable subset of the body.

`getBody` also controls key reuse detection. Do not include fields that change on every retry, such as timestamps or trace IDs:

```ts
getBody: (req) => ({
  amount: req.body.amount,
  currency: req.body.currency
});
```

## Failure behavior

| Situation                             | Result                                     |
| ------------------------------------- | ------------------------------------------ |
| Missing key, `requireKey: false`      | Route runs without idempotency protection. |
| Missing key, `requireKey: true`       | 400 `KEY_REQUIRED`.                        |
| Same key and same payload             | Stored result is returned.                 |
| Same key and different payload        | 409 `KEY_REUSED_WITH_DIFFERENT_REQUEST`.   |
| Same key while the first request runs | 409 `REQUEST_IN_PROGRESS`.                 |
| Same key after a permanent failure    | 409 `REQUEST_FAILED`.                      |
| Store throws                          | 503 `STORE_UNAVAILABLE`.                   |
| Cache throws                          | Request continues against the store.       |

`isPermanentError` defaults to `true` for every error. If you do not set it, one transient database error marks the key `FAILED`, and every retry returns 409 until cleanup deletes the record after 24 hours. Set it on every protected route.

A transient failure deletes the lock so the client can retry. The retry counter increments, and the third transient failure marks the key `FAILED`.

## Background jobs

Run both jobs on a schedule. They are methods on the handler and also standalone exports.

```ts
import { IdempotencyHandler } from "@/blocks/idempotency";

const handler = new IdempotencyHandler(store);

// Mark locks older than 5 minutes as failed.
await handler.recoverStuckRecords({ timeoutInMs: 5 * 60 * 1000, limit: 100 });

// Delete expired SUCCESS and FAILED records.
await handler.cleanupExpiredRecords({ limit: 500 });
```

`recoverStuckRecords` does not retry the operation. It marks abandoned `PROCESSING` records `FAILED`. A client retry with the same key then returns 409 `REQUEST_FAILED`. To run the operation again, use a new idempotency key or delete the record through your store. The public `retry` method only changes a `FAILED` record to `PROCESSING`; it does not execute the operation, and `execute` treats the key as in progress after that change.

If a legitimate operation can run longer than `timeoutInMs`, either raise the timeout or update the record's `updatedAt` through your store while the operation runs. Otherwise recovery can mark a live operation as failed, and a client can run it again with a new key.

`cleanupExpiredRecords` asks the store to delete at most `limit` records per run, default 500. The store must honor the limit. It never deletes `PROCESSING` records.

## Observability

`IdempotencyHandler` accepts a logger and metrics sink. The logger interface is duck-typed:

```ts
import { logger } from "@/blocks/logger/core";
import { IdempotencyHandler } from "@/blocks/idempotency";

const handler = new IdempotencyHandler(store, cache, { logger });
```

Metrics names:

- `idempotency_cache_hits_total`
- `idempotency_cache_misses_total`
- `idempotency_duplicates_total`
- `idempotency_store_errors_total`
- `idempotency_recovered_records_total`
- `idempotency_cleaned_records_total`
- `idempotency_latency_seconds`

The adapters attach context to each request when `attachContext` is true:

| Framework | Location                                         |
| --------- | ------------------------------------------------ |
| Express   | `res.locals.idempotency`                         |
| Fastify   | `request.idempotency`                            |
| Hono      | `getIdempotencyContext(c)` from the Hono adapter |

The Hono context key is `blockend.idempotency`. Read it with `getIdempotencyContext(c)`, not `c.get("idempotency")`.

## API reference

### `IdempotencyHandler`

```ts
class IdempotencyHandler {
  constructor(
    store: IdempotencyStore,
    cache?: IdempotencyCache,
    options?: { logger?: Logger; metrics?: Metrics }
  );

  execute(
    userId: string,
    operation: string,
    key: string,
    body: unknown,
    run: () => Promise<unknown>,
    options?: { isPermanentError?: (error: unknown) => boolean }
  ): Promise<unknown>;

  validateKey(key: unknown, options?: KeyValidationOptions): string;

  static serialize(value: unknown): string;
  hashRequest(body: unknown): string;

  retry(userId: string, operation: string, key: string): Promise<IdempotencyRecord | null>;

  cleanupExpiredRecords(options?: { limit?: number }): Promise<{ deleted: number }>;
  recoverStuckRecords(options?: {
    timeoutInMs?: number;
    limit?: number;
  }): Promise<{ processed: number; succeeded: number; failed: number }>;
}
```

`retry` changes a `FAILED` record to `PROCESSING` and does not execute the operation. A `SUCCESS` record is returned unchanged. A `PROCESSING` record throws `REQUEST_IN_PROGRESS`. After `retry` returns, `execute` also rejects the key as in progress, so use it only in a custom workflow that completes or releases the record through the store.

## When not to use it

- Read-only endpoints. There is nothing to deduplicate.
- Operations that cannot tolerate a 24 hour key lifetime and have retry windows longer than that.
- Systems that need exactly-once across multiple services. This block provides a single-store guarantee, not a distributed transaction.
- Stores without atomic create. Two concurrent requests can both acquire the lock.
