The **Idempotency** block makes retries safe. When a client retries the same request — because a network connection dropped, a timeout fired, or a payment form was double-submitted — the block guarantees your business logic runs **exactly once**, and every retry receives the stored result of the first attempt.

It wraps a piece of business logic in an atomic lock keyed by `(userId, operation, idempotency-key)`. The first request acquires the lock and executes; every duplicate request either replays the stored response or is rejected with a precise error. This is the same pattern used by Stripe's `Idempotency-Key` header.

> **Production tip:** the block ships two parts — a framework-agnostic core (`IdempotencyHandler` + pluggable `IdempotencyStore` / `IdempotencyCache` interfaces) and adapters for Express, Fastify, and Hono. You can use the core with any framework by implementing the two interfaces, or drop an adapter in and go. For a full production walkthrough (keys, stores, error classification, observability, and failure modes), see [Idempotency in Production](/docs/03-guides/02-idempotency-in-production).

---

## Features

- Exactly-once execution via an atomic database lock (`PROCESSING` record)
- Replays the stored response for duplicate requests without re-running logic
- Deterministic request hashing — SHA-256 over a key-order-independent serialization
- Pluggable `IdempotencyStore` and L1 `IdempotencyCache` interfaces (the core is framework- and ORM-agnostic)
- Key validation and sanitization — trimming, length limits, charset, optional UUID enforcement
- Constant-time hash comparison so hash probing can't leak prefix information
- Permanent vs transient failure classification — poisons the key after 3 transient retries
- Background jobs: expired-record cleanup and stuck-lock recovery for crashed workers
- Collision-proof, length-prefixed cache keys that keep tenants and operations isolated
- Optional structured logging and metrics hooks with noop defaults
- Adapters for Express, Fastify, and Hono — each with a route wrapper (plus a capture middleware for Express and Hono), and a shared error-code → HTTP status mapping

## Configuration

### IdempotencyHandlerOptions

| Option    | Type      | Default       | Required | Description                                                |
| --------- | --------- | ------------- | -------- | ---------------------------------------------------------- |
| `logger`  | `Logger`  | `noopLogger`  | No       | Structured logger. Accepts any pino/winston-shaped logger. |
| `metrics` | `Metrics` | `noopMetrics` | No       | Metrics sink. Emits counters and a latency histogram.      |

### KeyValidationOptions

| Option        | Type                         | Default            | Required | Description                                   |
| ------------- | ---------------------------- | ------------------ | -------- | --------------------------------------------- |
| `minLength`   | `number`                     | `1`                | No       | Minimum key length after trimming.            |
| `maxLength`   | `number`                     | `128`              | No       | Maximum key length after trimming.            |
| `requireUuid` | `boolean`                    | `false`            | No       | When `true`, the key must be a UUID v1–v5.    |
| `pattern`     | `{ value: RegExp, message }` | `[A-Za-z0-9._:-]+` | No       | Custom charset pattern and its error message. |

Keys are **trimmed first**, before any length or format check, so whitespace-only input can't bypass limits.

### ExpressIdempotencyOptions

| Option             | Type                                            | Default                           | Required | Description                                                          |
| ------------------ | ----------------------------------------------- | --------------------------------- | -------- | -------------------------------------------------------------------- |
| `key`              | `IdempotencyKeySource`                          | header only                       | No       | Where to look for the key: `header`, `bodyField`, `queryParam`.      |
| `requireKey`       | `boolean`                                       | `false`                           | No       | When `true`, a request without a key is rejected with 400.           |
| `getUserId`        | `(req) => string \| undefined`                  | `req.user?.id` or `"anonymous"`   | No       | Resolves the tenant/user id that scopes the key.                     |
| `getOperation`     | `(req) => string`                               | `` `${req.method}:${req.path}` `` | No       | Resolves the operation name.                                         |
| `getBody`          | `(req) => unknown`                              | `req.body ?? {}`                  | No       | Resolves the payload to hash.                                        |
| `isPermanentError` | `(err) => boolean`                              | `() => true`                      | No       | Classifies failures as permanent (mark FAILED) or transient (retry). |
| `attachContext`    | `boolean`                                       | `true`                            | No       | Attaches metadata to `res.locals.idempotency`.                       |
| `statusMap`        | `Partial<Record<IdempotencyErrorCode, number>>` | `{}`                              | No       | Overrides the default error-code to HTTP-status mapping.             |

> **Security:** the default `getUserId` falls back to `"anonymous"`. If `req.user` is unset, every request shares one global scope — any client that learns a key and payload could replay another client's stored response. Always provide a real, authenticated per-user id in production.

## Architecture

```text
Request (Idempotency-Key header / body field / query param)
   │
   ▼
Adapter (express.ts)
   │  resolves userId, operation, payload
   ▼
IdempotencyHandler.execute()
   │
   ├── 1. validateKey(key)            → trimmed, length + charset checked
   ├── 2. hashRequest(body)           → SHA-256 of deterministic serialization
   ├── 3. L1 cache check (CacheManager)
   │       ├── HIT + hash matches     → return stored response immediately
   │       ├── HIT + hash mismatch    → 409 KEY_REUSED_WITH_DIFFERENT_REQUEST
   │       └── MISS / cache down      → continue (DB is source of truth)
   ├── 4. Atomic store insert (PROCESSING lock)
   │       ├── CREATED                → lock acquired; run business logic
   │       ├── DUPLICATE + SUCCESS    → return stored response
   │       ├── DUPLICATE + PROCESSING → 409 REQUEST_IN_PROGRESS
   │       ├── DUPLICATE + FAILED     → 409 REQUEST_FAILED
   │       └── hash mismatch          → 409 KEY_REUSED_WITH_DIFFERENT_REQUEST
   ├── 5. execute() succeeds
   │       └── mark record SUCCESS → write L1 cache (non-blocking)
   └── 6. execute() fails
           ├── permanent error  → mark record FAILED (key poisoned)
           └── transient error  → increment retry counter
                  ├── < 3 retries → delete record (lock released)
                  └── ≥ 3 retries → mark record FAILED
```

### Lifecycle of a request

1. **Key resolution** — the adapter extracts the key from the header, body field, or query parameter. With `requireKey: true`, a missing key is rejected up front with 400.
2. **Validation and hashing** — the key is trimmed and validated; the payload is hashed deterministically so identical payloads always produce identical fingerprints regardless of key order.
3. **Cache fast-path** — if an L1 cache is configured and holds a matching entry, the stored response is returned without touching the database.
4. **Lock acquisition** — the store's `create` performs an atomic insert. Success means this request owns the lock; a duplicate means another request (past or present) owns the key.
5. **Execution** — the business logic runs exactly once, then the record is marked `SUCCESS` and the cache is written asynchronously.
6. **Failure classification** — permanent failures poison the key (`FAILED`); transient failures release the lock so the client can retry, until the retry budget is exhausted.

### Background jobs

- `cleanupExpiredRecords` — deletes expired `SUCCESS`/`FAILED` records so keys become reusable. It **never** deletes `PROCESSING` records, even expired ones — purging an active lock would let a duplicate request run concurrently. Run it on a cron schedule.
- `recoverStuckRecords` — finds `PROCESSING` records whose `updatedAt` is older than the timeout (a worker crashed mid-execution) and marks them `FAILED` so clients get a fast, safe retry. Each record is processed independently so one DB hiccup can't abort the batch.

## When to Use

- You have mutation endpoints where a client retry could double-execute — payments, refunds, order creation, webhook processing.
- Your API is consumed by clients that retry on timeouts or network failures and you want to return the original result instead of re-running the operation.
- You need to reject conflicting retries (same key, different payload) or concurrent duplicates explicitly, with clear HTTP semantics (409).
- You want a consistent, auditable record of which requests were deduplicated, with pluggable storage and optional metrics.

## When Not to Use

- **Read-only endpoints** — idempotency is only useful for state-changing operations.
- **Truly unique requests** — if every request is inherently one-off (for example, a chat message), the key adds overhead without benefit.
- **You need exactly-once across an entire distributed system** — this block deduplicates within one service and its store. Cross-service exactly-once needs a shared transactional store and a distributed consensus strategy on top.
- **Your store can't guarantee an atomic create** — the lock depends on `create` returning `CREATED`/`DUPLICATE` atomically (for example, a unique constraint). Without it, two concurrent requests could both acquire the lock.

## Usage

The Express adapter supports two styles, plus a framework-agnostic core path for other frameworks.

### Express — `idempotent()` wrapper

Use this when your route logic **returns** the response payload. The wrapper runs it inside `handler.execute`, stores the result, and sends it with `res.json`.

```ts
import express from "express";
import { IdempotencyHandler } from "@/blocks/idempotency";
import { idempotent } from "@/blocks/idempotency/adapters/express";
import { createCharge } from "./charges";

const app = express();
app.use(express.json());

// Provide a real per-user id — never rely on the "anonymous" default in production.
const handler = new IdempotencyHandler(myStore, myCache, {
  logger: myLogger,
  metrics: myMetrics
});

app.post(
  "/payments",
  idempotent(
    handler,
    async (req) => {
      const charge = await createCharge(req.body);
      return { id: charge.id, status: charge.status };
    },
    {
      getUserId: (req) => req.user.id,
      getOperation: (req) => "payments:create",
      isPermanentError: (err) => err instanceof ValidationError
    }
  )
);
```

The first request with a given `Idempotency-Key` runs `createCharge` once. Every retry with the same key and payload returns the stored `{ id, status }` without re-running.

### Express — `idempotencyMiddleware()`

Use this when your route already sends its own response with `res.json(...)`. The middleware intercepts the JSON body your route sends, stores it as the idempotent response, and replays it on duplicates.

```ts
import express from "express";
import { IdempotencyHandler } from "@/blocks/idempotency";
import { idempotencyMiddleware } from "@/blocks/idempotency/adapters/express";

const app = express();
app.use(express.json());

const handler = new IdempotencyHandler(myStore);

app.post("/payments", idempotencyMiddleware(handler, { requireKey: true }), async (req, res) => {
  const charge = await createCharge(req.body);
  res.json(charge);
});
```

If the downstream chain responds with a 4xx/5xx status, the middleware marks the record `FAILED` instead of `SUCCESS` — an error body is never stored as a successful result.

### Fastify

```ts
import Fastify from "fastify";
import { IdempotencyHandler } from "@/blocks/idempotency";
import { idempotent } from "@/blocks/idempotency/adapters/fastify";

const app = Fastify({ logger: true });

const handler = new IdempotencyHandler(myStore, myCache, {
  logger: myLogger,
  metrics: myMetrics
});

// The route can RETURN the payload (Fastify sends it)…
app.post(
  "/payments",
  idempotent(handler, async (request) => {
    const charge = await createCharge(request.body);
    return { id: charge.id, status: charge.status };
  })
);

// …or call reply.send — the payload is captured and replayed either way.
app.post(
  "/refunds",
  idempotent(handler, async (request, reply) => {
    reply.send(await createRefund(request.body));
  })
);
```

The wrapper resolves `userId`, `operation`, and `body` from the request by default (`request.user?.id`, `METHOD:routerPath`, `request.body`), and every option hook from `ExpressIdempotencyOptions` is available (`getUserId`, `getOperation`, `getBody`, `isPermanentError`, `requireKey`, `statusMap`, ...). The per-request context is attached to `request.idempotency` (readable in hooks) — TypeScript types are augmented automatically.

### Hono

```ts
import { Hono } from "hono";
import { IdempotencyHandler } from "@/blocks/idempotency";
import { idempotent, idempotencyMiddleware } from "@/blocks/idempotency/adapters/hono";

const app = new Hono();
const handler = new IdempotencyHandler(myStore);

// Wrapper style — the route returns the payload (or an already built Response):
app.post(
  "/payments",
  idempotent(handler, async (c) => {
    const charge = await createCharge(await c.req.json());
    return { id: charge.id, status: charge.status };
  })
);

// Capture style — the route sends its own response with c.json:
app.post("/refunds", idempotencyMiddleware(handler, { requireKey: true }), async (c) => {
  const refund = await createRefund(await c.req.json());
  return c.json(refund);
});
```

The payload is hashed from a **non-consuming clone** of the request body, so the route can still call `await c.req.json()` after the wrapper/middleware has read it. The per-request context is available to the route via `getIdempotencyContext(c)` (or `c.get("idempotency")`) — it carries the key, user, operation, and outcome, and flips from `"processing"` to `"completed"`/`"failed"` once execution settles.

### Framework-Agnostic Core

No Express? Implement the `IdempotencyStore` interface (and optionally `IdempotencyCache`) and call the handler directly from any framework handler:

```ts
import { IdempotencyHandler } from "@/blocks/idempotency";

const handler = new IdempotencyHandler(myStore, myCache);

app.post("/payments", async (req, res) => {
  try {
    const result = await handler.execute(
      req.user.id,
      "payments:create",
      req.headers["idempotency-key"],
      req.body,
      () => createCharge(req.body)
    );
    res.json(result);
  } catch (error) {
    if (error instanceof IdempotencyError) {
      return res.status(statusFor(error.code)).json({
        error: { code: error.code, message: error.message }
      });
    }
    throw error;
  }
});
```

## API Reference

#### IdempotencyHandler

```ts
class IdempotencyHandler
```

Wraps business logic so retries of the same request are safe: a request keyed by `(operation, userId, key)` executes exactly once, and subsequent attempts receive the stored result instead.

##### new IdempotencyHandler(store, cache?, options?)

| Parameter | Type                        | Required | Description                                 |
| --------- | --------------------------- | -------- | ------------------------------------------- |
| `store`   | `IdempotencyStore`          | Yes      | The persistent record store.                |
| `cache`   | `IdempotencyCache`          | No       | Optional L1 cache for fast replays.         |
| `options` | `IdempotencyHandlerOptions` | No       | `logger` and `metrics` (see Configuration). |

##### execute

```ts
execute(
  userId: string,
  operation: string,
  key: string,
  body: unknown,
  execute: () => Promise<unknown>,
  options?: { isPermanentError?: (err: unknown) => boolean },
): Promise<unknown>
```

Main entrypoint. Validates the key, hashes the body, checks the cache, acquires the atomic lock, runs `execute()`, and records the outcome. Returns the business-logic result (fresh or replayed).

##### validateKey

```ts
validateKey(key: unknown, options?: KeyValidationOptions): string
```

Sanitizes and validates an idempotency key, returning the cleaned value. **Always use the returned value**, not the raw input. Throws `IdempotencyError` on invalid keys.

##### serialize

```ts
static serialize(value: unknown): string
```

Deterministically stringifies a payload (recursively sorted keys, order-preserving arrays). Rejects `undefined`, `NaN`, `±Infinity`, `BigInt`, functions, symbols, cycles, and nesting beyond 100 levels.

##### hashRequest

```ts
hashRequest(body: unknown): string
```

Returns a stable SHA-256 fingerprint (64-char lowercase hex) of a payload. Identical payloads hash identically regardless of key order.

##### cleanupExpiredRecords

```ts
cleanupExpiredRecords(options?: { limit?: number }): Promise<{ deleted: number }>
```

Deletes expired `SUCCESS`/`FAILED` records. `PROCESSING` records are never touched here — run this from a cron job.

##### recoverStuckRecords

```ts
recoverStuckRecords(options?: { timeoutInMs?: number; limit?: number }): Promise<RecoveryResult>
```

Marks `PROCESSING` records older than `timeoutInMs` (default 5 minutes) as `FAILED`. Returns `{ processed, succeeded, failed }`.

##### retry

```ts
retry(userId: string, operation: string, key: string): Promise<IdempotencyRecord | null>
```

Re-opens a `FAILED` record to `PROCESSING` for a manual retry. Throws `REQUEST_IN_PROGRESS` if the record is already processing.

#### IdempotencyStore

```ts
interface IdempotencyStore
```

The contract your database adapter implements. See [Manual File Setup](#blocksidempotencyinterfacesstorets) for the full interface.

| Method                     | Description                                                                  |
| -------------------------- | ---------------------------------------------------------------------------- |
| `create(record)`           | Atomic insert; returns `{ status: "CREATED" }` or `{ status: "DUPLICATE" }`. |
| `find(key, op, user)`      | Fetch a record by its composite key.                                         |
| `findAll(filters?)`        | Query records for background jobs (by status, updated-before, limit).        |
| `markSuccess(...)`         | Record a successful response.                                                |
| `markProcessing(...)`      | Re-acquire the lock.                                                         |
| `markFailed(...)`          | Poison the record.                                                           |
| `incrementRetryCount(...)` | Increment a retry counter that **survives record deletion**.                 |
| `delete(...)`              | Release the lock (used after transient failures).                            |
| `deleteExpired(params)`    | Bulk-delete expired records by status.                                       |

> **Retry counter contract:** after a transient failure the handler deletes the record so the client can retry, then creates a fresh one. If the retry counter lived on the row, it would reset on re-creation and `MAX_ALLOWED_RETRIES` would never be reached. Keep the count in a location that outlives the row (for example, a dedicated counter table or column upserted by key).

#### IdempotencyCache

```ts
interface IdempotencyCache {
  get(
    key: string
  ): Promise<
    { status: "HIT"; data: CachedResponse } | { status: "MISS" } | { status: "UNAVAILABLE" }
  >;
  set(key: string, value: CachedResponse, ttl: number): Promise<void>;
  delete(key: string): Promise<void>;
}
```

Optional L1 cache. Failures are swallowed — the database remains the source of truth.

#### IdempotencyError

```ts
class IdempotencyError extends Error {
  readonly code: IdempotencyErrorCode;
}
```

Typed error carrying a machine-readable code. The Express adapter maps codes to HTTP statuses; `IdempotencyError` also helps you distinguish idempotency failures from infrastructure errors when using the core directly.

| Code                                                                                                                   | HTTP (Express adapter) | Meaning                                    |
| ---------------------------------------------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------ |
| `KEY_INVALID_TYPE`, `KEY_REQUIRED`, `KEY_TOO_SHORT`, `KEY_TOO_LONG`, `KEY_INVALID_FORMAT`, `UNSUPPORTED_REQUEST_VALUE` | 400                    | Client input problems.                     |
| `KEY_REUSED_WITH_DIFFERENT_REQUEST`                                                                                    | 409                    | Same key, different payload.               |
| `REQUEST_IN_PROGRESS`                                                                                                  | 409                    | A concurrent request holds the lock.       |
| `REQUEST_FAILED`                                                                                                       | 409                    | The previous attempt with this key failed. |
| `RECORD_NOT_FOUND`                                                                                                     | 404                    | Lookup miss.                               |
| `STORE_UNAVAILABLE`, `CACHE_UNAVAILABLE`                                                                               | 503                    | Infrastructure failure.                    |
| `INVALID_CACHED_RESPONSE`                                                                                              | 500                    | Corrupt cache entry (should not happen).   |

Override the mapping per-route with `statusMap`.

## Examples

### Basic Express Setup

```ts
import express from "express";
import { IdempotencyHandler } from "@/blocks/idempotency";
import { idempotent } from "@/blocks/idempotency/adapters/express";

const app = express();
app.use(express.json());

const handler = new IdempotencyHandler(myStore);

app.post(
  "/orders",
  idempotent(handler, async (req) => {
    const order = await createOrder(req.body);
    return { id: order.id, status: "created" };
  })
);
```

### Classifying Transient vs Permanent Failures

```ts
app.post(
  "/payments",
  idempotent(handler, async (req) => createCharge(req.body), {
    // Validation errors are permanent — the key is poisoned immediately.
    // Network/database blips are transient — the lock is released so the
    // client can retry (up to 3 attempts).
    isPermanentError: (err) =>
      err instanceof ValidationError || err instanceof InsufficientFundsError
  })
);
```

### Background Jobs (cron)

Run both jobs on a schedule so keys become reusable and crashed workers never leave permanent locks:

```ts
import { IdempotencyHandler } from "@/blocks/idempotency";

const handler = new IdempotencyHandler(myStore);

// Every hour: purge expired SUCCESS/FAILED records.
await handler.cleanupExpiredRecords({ limit: 500 });

// Every 5 minutes: fail records stuck in PROCESSING longer than 5 minutes.
const recovery = await handler.recoverStuckRecords({ timeoutInMs: 5 * 60 * 1000 });
console.log(recovery); // { processed, succeeded, failed }
```

### Adding an L1 Cache

```ts
import { IdempotencyHandler, type IdempotencyCache } from "@/blocks/idempotency";

// Wrap your Redis client (ioredis, node-redis, ...) in the 3-method interface:
const cache: IdempotencyCache = {
  async get(key) {
    const raw = await redis.get(key);
    return raw ? { status: "HIT", data: JSON.parse(raw) } : { status: "MISS" };
  },
  async set(key, value, ttl) {
    await redis.set(key, JSON.stringify(value), "PX", ttl);
  },
  async delete(key) {
    await redis.del(key);
  }
};

const handler = new IdempotencyHandler(myStore, cache);
```

The cache is a fast path only: if Redis is down, requests fall back to the store, which remains the source of truth.

### Bridging Your Logger

```ts
import { IdempotencyHandler } from "@/blocks/idempotency";
import { createLoggerAdapter } from "@/blocks/idempotency/utils/create-logger";

const logger = createLoggerAdapter((level, msg, meta) => {
  console[level](msg, meta ?? "");
});

const handler = new IdempotencyHandler(myStore, undefined, { logger });
```

## Related Blocks

- **Logger** — pass any pino-style logger via `IdempotencyHandlerOptions.logger`, or use `createLoggerAdapter` to bridge your existing logger. Structured context (`key`, `userId`, `operation`) is included on every log line.

## FAQ

**What happens when a client retries with the same key and payload?**  
The stored response is returned without re-running the business logic — whether from the L1 cache (fast path) or the store record.

**What happens when the same key is reused with a different payload?**  
The request is rejected with `KEY_REUSED_WITH_DIFFERENT_REQUEST` (409). Hashes are compared in constant time so the rejection leaks no prefix information.

**What happens when two identical requests arrive concurrently?**  
The second one hits the `PROCESSING` lock and receives `REQUEST_IN_PROGRESS` (409). Once the first finishes, retries replay the stored response.

**When is a key released after a failure?**  
Permanent failures mark the record `FAILED` (the key is poisoned). Transient failures release the lock so the client can retry — up to `MAX_ALLOWED_RETRIES` (3), after which the key is poisoned with `REQUEST_FAILED`.

**Are keys global across users?**  
No — the scope is `(userId, operation, key)`. The same key used by two different users or for two different operations is treated as two independent requests. However, if `getUserId` resolves to the default `"anonymous"`, all keys become global. Always provide a real user id.

**What if my store or cache is down?**  
Store failures surface as `STORE_UNAVAILABLE` (503). Cache failures are swallowed and requests fall back to the store, which remains the source of truth.

**How long do records live?**  
Records and cache entries default to a 24-hour TTL. Run `cleanupExpiredRecords` on a schedule to purge expired `SUCCESS`/`FAILED` records so keys become reusable.

**Why won't cleanup delete an expired `PROCESSING` record?**  
Purging an active lock would let a duplicate incoming request acquire a fresh lock and run concurrently. Stuck locks are handled by `recoverStuckRecords` instead.

**What payload values are rejected by hashing?**  
`undefined`, `NaN`, `±Infinity`, `BigInt`, functions, symbols, cyclic references, and nesting deeper than 100 levels are rejected with `UNSUPPORTED_REQUEST_VALUE` — they can't be hashed deterministically.
