The logger block gives your app one Pino instance. Each request gets an ID, log lines written during that request include the ID, and the framework adapters log the request method, path, status, and duration after the handler runs.

There is no root `index.ts`. Import the shared logger from `core` and adapters from `adapters/`.

<Callout type="warn">
  The core uses `pino-pretty` when `NODE_ENV` is not `production`. The CLI installs `pino` but not `pino-pretty`. Add it as a dev dependency, or the logger will fail at startup outside production:

```bash
pnpm add -D pino-pretty
```

With npm, run `npm install -D pino-pretty`.

</Callout>

## Quick start

```bash
pnpm dlx blockend-cli init
pnpm dlx blockend-cli add logger
```

```ts
import express from "express";
import { expressLoggerAdapter } from "@/blocks/logger/adapters/express";
import { logger } from "@/blocks/logger/core";

const app = express();

app.use(expressLoggerAdapter);

app.get("/", (_req, res) => {
  logger.info("Handling request");
  res.json({ ok: true });
});
```

## Framework setup

### Express

```ts
import express from "express";
import { expressLoggerAdapter } from "@/blocks/logger/adapters/express";

const app = express();

app.use(expressLoggerAdapter);
```

The adapter sets `req.id`, generates a UUID when `x-request-id` is missing, and logs after `res` emits `finish`.

### Fastify

```ts
import Fastify from "fastify";
import { fastifyLogger } from "@/blocks/logger/adapters/fastify";

const app = Fastify();

await app.register(fastifyLogger);
```

The adapter adds `request.requestId` and registers `onRequest` and `preHandler` hooks. Register it before your routes.

### Hono

```ts
import { Hono } from "hono";
import { honoLoggerAdapter } from "@/blocks/logger/adapters/hono";

type Variables = {
  requestId: string;
};

const app = new Hono<{ Variables: Variables }>();

app.use("*", honoLoggerAdapter());

app.get("/", (c) => {
  return c.json({ requestId: c.get("requestId") });
});
```

Declare the `requestId` variable in your Hono type so `c.get("requestId")` is typed.

## Request context

`runWithLoggerContext` creates an `AsyncLocalStorage` scope. The adapters use it for HTTP requests. Use it directly for background jobs and queue workers:

```ts
import { logger, runWithLoggerContext } from "@/blocks/logger/core";

await runWithLoggerContext(null, async (requestId) => {
  logger.info({ jobId: "job_123", requestId }, "Processing job");
});
```

Pass an existing ID as the first argument to reuse it:

```ts
await runWithLoggerContext("job_123", async () => {
  logger.info("Processing job");
});
```

`getRequestId()` returns the current ID or `undefined` outside a context.

```ts
import { getRequestId } from "@/blocks/logger/core";

const id = getRequestId();
```

## Configuration

The logger is configured in `core.ts`, not through a factory. Edit the file to change it:

```ts
const isProduction = process.env.NODE_ENV === "production";

export const logger = pino({
  level: isProduction ? "info" : "debug",
  mixin() {
    const store = loggerContext.getStore();
    return store ? { requestId: store.requestId } : {};
  },
  redact: {
    paths: ["Authorization", "*.token", "token", "*.password", "password"],
    censor: "[REDACTED]"
  },
  ...(isProduction
    ? {}
    : {
        transport: {
          target: "pino-pretty",
          options: {
            colorize: true,
            translateTime: "SYS:standard",
            ignore: "hostname,pid"
          }
        }
      })
});
```

| Setting              | Value                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------- |
| Level                | `debug` outside production, `info` in production                                      |
| Request ID field     | `requestId`                                                                           |
| Redacted fields      | `Authorization`, `token`, `password`, and one nested level for `token` and `password` |
| Dev transport        | `pino-pretty`                                                                         |
| Production transport | JSON to stdout                                                                        |

The redaction list is narrow. Add your own paths if your app logs cookies, API keys, or other secrets.

## API reference

### `logger`

A configured `pino.Logger`. It writes JSON in production and pretty output in development.

```ts
logger.info({ userId }, "User signed in");
logger.error({ err }, "Payment failed");
```

### `getRequestId`

```ts
function getRequestId(): string | undefined;
```

Returns the request ID from the current async context.

### `runWithLoggerContext`

```ts
function runWithLoggerContext<T>(
  incomingId: string | undefined | null,
  callback: (requestId: string) => T
): T;
```

Uses `incomingId` when it is a non-empty string. Otherwise it generates a UUID. The callback runs inside the new context.

### `loggerContext`

The `AsyncLocalStorage<LoggerContext>` instance. Use it only if you need to inspect or replace the store directly.

### Adapters

| Adapter | Export                 | Adds                                     |
| ------- | ---------------------- | ---------------------------------------- |
| Express | `expressLoggerAdapter` | `req.id`, response finish log            |
| Fastify | `fastifyLogger`        | `request.requestId`, response finish log |
| Hono    | `honoLoggerAdapter`    | `c.set("requestId", id)`, response log   |

All adapters read `x-request-id` when present and generate a UUID otherwise.

## Production notes

- Keep JSON logs in production. Pretty printing costs CPU and is harder to parse.
- Ship logs to a collector. stdout alone is not durable on most platforms.
- The adapters log one line per request that returns normally. They do not log request bodies or headers. A request that throws past the Hono adapter does not produce a completion line.
- The incoming `x-request-id` header is trusted. If clients can set it, validate the format before you use it for tracing.
- Error objects logged as `{ err }` are serialized by Pino with their stack trace. Do not log secrets in error messages.

## When not to use it

- You already have a configured Pino, Winston, or OpenTelemetry logger.
- You need distributed tracing. Request IDs are not trace spans. Use OpenTelemetry for that.
- You need audit logs with retention and tamper protection. Use a dedicated audit system.
